# VR180 output, and playing back on Quest 3 and Apple Vision Pro

Plan only — nothing here is implemented. Branch: `vr180`, off `5d59e84`.

## The constraint that shapes everything

**The 360 path must not regress.** It works, it has been tuned against real
headset viewing, and the recent stereo geometry and cube seam fixes were
expensive to find. Nothing in this plan is worth breaking that.

That is not a hope, it is a design rule with consequences, and they are set out
in [Not breaking 360](#not-breaking-360) below. The short version: 180 is a new
*mode* selected explicitly, every shared function keeps its current behaviour as
the default, and the existing tests stay untouched and passing.

---

## 1. What already works, unchanged

Worth stating first, because it is most of the hard-won part.

### The stereo warp needs no change

This is the surprising one. The instinct is that a narrower field needs
different stereo geometry. It does not — the omnidirectional warp
(`warp._eye_offset`) is field-of-view agnostic, and it is exactly what VR180
wants.

The alternative would be a fixed baseline, matching what a real two-lens VR180
rig produces. That has disparity falling off as `cos(longitude)`, reaching
**zero at ±90°** — the extreme left and right of a 180° field. That is
precisely the defect fixed in the 360 path, where it made the far half of a
scene painful to look at. A real rig genuinely has that flaw. There is no
reason to reproduce it in synthesised content.

### Also unchanged

- Depth backends and model selection
- `_fit_and_apply` — the per-face affine solver takes sample pairs and does not
  care where they came from
- The encoder, hardware encoder probing, chroma and colour handling
- The bit-depth warning, progress/cancel plumbing, NDJSON events
- The desktop UI, apart from one new control

### Smaller than expected: the metadata

`spherical.py` already carries most of it:

- `_STEREO_MODES` (line 46) already includes `"left-right": 2`
- `inject_spherical_metadata` already takes `stereo_mode` as a parameter

Only the projection bounds are missing. `_sv3d()` (line 66) hardcodes an `equi`
box with all-zero bounds, which means "covers the whole sphere":

```python
equi = _full_box("equi", struct.pack(">IIII", 0, 0, 0, 0))
```

For VR180 those bounds describe the crop. Needs to become a parameter, not a
rewrite.

## 2. What actually needs building

### 2.1 Face layout for a hemisphere — the main job

**Why it is not optional.** Feed a 180° source to the current six faces and
four of them come back half black. A relative-depth model normalises against
what it sees, so a half-black face produces a depth map normalised against the
black. That is not wasted compute, it is *wrong output*.

**What is needed.** A face set covering only the front hemisphere. The
machinery is close to hand — `_FACE_BASIS` is a dictionary of basis vectors,
and `_overlap_face_dirs` already builds arbitrary-FOV faces from one — but two
things assume a closed cube:

- `_face_local_coords` resolves a direction to its owning face across all six
- `align_overlapping_faces` finds face pairs by asking which face owns each
  sampled direction

For a hemisphere those need an explicit adjacency set rather than a lookup over
the whole cube.

**Open design question**, worth settling before writing anything: whether a
hemisphere is best covered by a subset of cube faces, or by a purpose-built
layout (for example one centre face plus four surrounding at a shallower
angle). The cube exists because it tiles a *sphere* evenly; it has no special
claim on a hemisphere.

### 2.2 Longitude wrap must become clamp — seven sites

In 360 the left and right edges of a frame are the same place. In 180 they are
90° apart. Every wrap is wrong in the new mode, and each will show as content
bleeding from one edge of the field to the other — subtle on a monitor, obvious
in a headset.

| File | Line | What |
|---|---|---|
| `projection.py` | 283 | `equirect_to_cubemap` — `BORDER_WRAP` |
| `projection.py` | 882 | `equirect_to_overlapping_faces` — `u % w` |
| `projection.py` | 886 | same — `BORDER_WRAP` |
| `warp.py` | 381 | `_directional_fill` — `np.mod(src, w)` |
| `warp.py` | 664 | pass 1 splat — `np.mod(u0, w)` |
| `warp.py` | 762, 767 | pass 2 — `su % w` and `BORDER_WRAP` |
| `warp.py` | 796 | hole fill — `BORDER_WRAP` |
| `warp_torch.py` | 228 | GPU pass 2 — `su.remainder(w)`, plus the wrapped
  column padding either side of the image |

Note the GPU path pads the image with one wrapped column on each side before
`grid_sample`, because it has no wrap mode. In 180 that padding must replicate
rather than wrap.

**This is the highest-risk item for the 360 path**, because every one of these
lines is on the hot path of working code. See
[Not breaking 360](#not-breaking-360).

### 2.3 Output layout: side-by-side

VR180 convention is left|right, not top/bottom. Two sites:

- `pipeline.py:644` — `_Sink.write`, `np.concatenate([left, right], axis=0)`
- `pipeline.py:874` — `preview_frame`, same

Trivial in itself. Interacts with frame size — see below.

### 2.4 Metadata

- Pass `stereo_mode="left-right"` at `pipeline.py:773` when in 180 mode
- Parameterise `_sv3d()` bounds. For a 180°×180° hemisphere in a square frame,
  the horizontal bounds crop 25% from each side (leaving the middle 50% of a
  full sphere = 180°) and the vertical bounds are zero. Values are 0.32 fixed
  point.
- **Spherical Video V1** (the `uuid` + RDF/XML block, `spherical.py:34`) has no
  way to express a partial sphere. Either omit V1 in 180 mode or accept that a
  V1-only reader will misinterpret the file. Omitting is probably correct;
  worth checking what still relies on V1.

### 2.5 Input handling

- `READABLE_PROJECTIONS` (`pipeline.py:524`) gains a half-equirect entry
- `resolve_projection` learns to detect it. Note that detection from metadata
  alone is unreliable: many VR180 files are tagged as equirect with `equi`
  bounds, and plenty are tagged as nothing at all. A 1:1 aspect ratio is a
  strong hint but not proof, so an explicit `--input-projection` override
  matters more here than it does for 360.
- `source_geometry` derives face size and working resolution differently

## 3. Two things that get better

**Speed.** A quarter of the solid angle and fewer faces to run depth on.
Expect roughly 2–3× faster than the equivalent 360 render.

**Frame size — and this one matters more than it looks.** HEVC caps the
decoded picture at **35,651,584 luma samples at every level, including 6.2**.
Width and height individually are fine well beyond 8192; it is the total that
is capped.

| Output | Frame | Megapixels | Within HEVC's cap |
|---|---|---|---|
| 360 top-bottom, 8K source | 7680×7680 | 59.0 | **no — 1.65× over** |
| 360 top-bottom, 5.7K source | 5760×5760 | 33.2 | yes |
| **180 side-by-side, 4096/eye** | 8192×4096 | 33.6 | **yes** |
| 180 side-by-side, 4800/eye | 9600×4800 | 46.1 | no |

So the current flagship 360 output is out of spec, and the VR180 format that
is gaining traction happens to land just inside. That is not a coincidence —
it is part of why it is gaining traction.

**Needs verifying against the spec text and against real devices before being
relied on.** Decoders vary: some accept over-spec streams, some refuse. The
existing 360 renders have been viewed through YouTube, which transcodes, so
local decode has never actually been tested.

---

## 4. One thing that gets worse

**Disocclusion at the field edge.** Warping the second eye shifts everything
sideways. In 360 there is always neighbouring content to shift in, because the
image wraps. In 180 there is genuinely nothing beyond the edge — one side of
the frame ends up with a strip the second eye has no source for.

This is missing information, not a bug. Options: crop a few degrees off that
edge, let the existing inpainting handle it, or render a slightly wider field
than delivered and trim. Worth deciding before building, because it affects
whether the working resolution is larger than the output.

## 5. Device targets

### Quest 3

Reads Google Spherical Video V2 — the boxes this project already writes. With
`left-right` stereo mode and correct `equi` bounds, a VR180 file should be
recognised natively. This is the lower-risk target and should be made to work
first.

### Apple Vision Pro

Three tiers, in increasing order of work and decreasing order of certainty:

**Tier 1 — third-party player.** A standard MP4, side-by-side, equirect-with-
bounds. Several 360/180 players on visionOS read this, and most allow the
layout to be set manually if metadata is not picked up. That manual override is
the safety net: even if nothing reads the boxes, the file still plays.
*Should work with exactly the Tier-1 Quest output — one file, both devices.*

**Tier 2 — native Photos playback.** Apple's immersive handling uses its own
signalling rather than Google's. Recent visionOS added native 180°/360°
support through Apple's projected-media metadata. In principle both sets of
boxes can live in one file, since unknown boxes are skipped — which would give
one file that is native on both devices. **Unverified.** I do not know Apple's
current requirements well enough to commit to this, and it needs checking
against the actual specification before any work starts.

**Tier 3 — MV-HEVC.** Apple's native spatial video packs two views into a
single HEVC stream. This is a codec-level change, not a metadata one: a
different encoder path, and ffmpeg support for MV-HEVC encoding needs checking
before assuming it is available at all. Substantial, and clearly a separate
milestone.

### Recommended target

**Tier 1 only, initially.** One file, side-by-side VR180, Google Spherical V2.
Native on Quest 3, plays on Vision Pro through a third-party player. Tiers 2
and 3 are separate pieces of work that should not hold up a working 180
pipeline.

## 6. Not breaking 360

The explicit requirement, so it gets its own section.

### Rules

1. **180 is an explicit mode, never inferred silently.** A new
   `--projection-out` (or equivalent) defaulting to the current behaviour.
   Auto-detection of 180 *input* may warn and suggest, but must not switch
   modes on its own — a misdetected 360 file silently rendered as 180 would be
   a bad failure.

2. **Every shared function keeps its current behaviour as the default.** New
   parameters default to the 360 value. `_eye_offset(dist, d, baseline)` gains
   nothing; the wrap sites gain a flag that defaults to wrapping.

3. **The existing test suite is not edited.** 356 tests pass on `main`. If a
   change to a shared function requires editing an existing test, that is the
   signal that the change altered 360 behaviour — stop and reconsider rather
   than update the test. The one exception is a test that is *itself* wrong,
   which has happened twice in this project and both times was worth arguing
   about explicitly first.

4. **Wrap handling is the sharpest edge.** Seven sites on hot paths in working
   code. Preference: a single module-level helper that both modes call, rather
   than seven independent conditionals. One place to get right, one place to
   test.

5. **A characterisation test before touching anything.** Render a few frames of
   `input2.mp4` on `main`, keep the output, and assert byte-identical (or
   within encoder noise) output after each change. Cheap, and it catches
   accidental 360 changes that unit tests would not.

### What to watch

The riskiest single change is 2.2, the wrap sites. The second riskiest is
anything touching `_face_local_coords`, which the cube seam alignment depends
on and which was hard to get right.

## 7. Suggested order

Each step should leave 360 working and tests green.

1. **Spike, throwaway.** Pad a 180 source into a full equirect canvas, run the
   existing pipeline unchanged, crop the result. Roughly 4× the necessary work
   and the empty hemisphere will corrupt depth normalisation — but it answers
   the only question that matters up front: *does depth estimation hold up on
   180 footage at all?* Do not build on it.
2. **Characterisation test** for the 360 path (rule 5 above).
3. **Metadata**: `equi` bounds parameter, `left-right` mode. Testable in
   isolation, no pipeline changes, immediately verifiable on a device with a
   hand-made file.
4. **Side-by-side stacking** behind the mode flag.
5. **Wrap → clamp**, via one shared helper.
6. **Hemisphere face layout** — the real work, and the part with a design
   decision in it.
7. **Input detection** and the UI control.
8. Device testing on Quest 3, then Vision Pro.

Steps 3 and 4 alone would let a hand-built side-by-side file be tested on both
headsets, which de-risks the whole of section 5 before the expensive work in
step 6.

## 8. To verify before building

Flagged rather than assumed:

- **HEVC maximum luma picture size** — the 35,651,584 figure and its
  application to 7680×7680 comes from recollection of the level tables. Check
  the spec text, then check what a Quest 3 and a Vision Pro actually refuse.
- **Whether current 360 output plays from a local file** on either headset.
  All viewing so far has been through YouTube, which transcodes. If local
  playback already fails at 8K, that reframes the resolution question for both
  formats.
- **Apple's projected-media metadata requirements**, and whether Google's boxes
  can coexist with Apple's in one file.
- **ffmpeg MV-HEVC encoding support**, before Tier 3 is planned in any detail.
- **VR180 metadata in the wild** — how existing VR180 files are actually
  tagged, as opposed to how the specification says they should be. This decides
  how much weight input auto-detection can carry.
