# VR180 output from 360 footage

Plan. Branch `vr180`, off `5d59e84`. Nothing implemented yet beyond the phase 1
spike, which was throwaway.

## Scope: 360 input only

**The tool takes monoscopic 360 equirectangular input and can produce either
360 or VR180 output. It does not accept 180 input.** A deliberate limitation,
not an oversight.

VR180 was designed as a *stereo* format. Every camera that shoots it — Canon's
dual fisheye, Vuze XR, Insta360 EVO, Kandao QooCam — records two eyes. The
trade the format makes is "give up half the sphere, get stereo and better
resolution allocation". So a **monoscopic** half-equirect barely exists in the
wild: essentially only as a crop somebody already made from 360 footage, and
the right answer to that person is to bring the original.

Anyone who does have VR180 footage already has the 3D this tool would
synthesise.

### What that decision removes

Every genuinely hard problem came from 180 *input*, not 180 output:

| | needed for 180 input | needed for 360 → 180 |
|---|---|---|
| hemisphere face layout | the main job | **no** |
| wrap → clamp, seven hot-path sites | highest risk | **no** |
| field boundary through the nadir | yes | **no** |
| edge disocclusion | unavoidable data loss | **no** |

With a full sphere going in, the depth stage sees six real faces, the warp has
content beyond the crop boundary to shift in, and the result is *better* than
the 180-input path could have produced. What 180 input would have taken is kept
in the [appendix](#appendix-180-input-not-planned).

## Not breaking 360

This was the original constraint and the main worry: seven longitude-wrap sites
on hot paths in working code. **Scoping to 360 input removes that risk by
construction rather than by care.**

`projection.py`, `warp.py` and `warp_torch.py` are not touched. Depth and
warping run on the full sphere exactly as they do today; everything new happens
after the second eye exists.

Two rules still apply:

1. **180 output is an explicit mode**, never inferred. The default stays 360
   top-bottom.
2. **The existing test suite is not edited.** If a change requires editing one
   of the 356 passing tests, that is the signal it altered 360 behaviour.

A characterisation test — render a few frames on `main`, assert the output does
not move — is cheap insurance and worth having anyway.

## What needs building

### 1. Crop and restack

After the warp, take the 180° longitude band from each eye and stack them
left|right instead of top/bottom. Two sites: `pipeline.py:644` (`_Sink.write`)
and `pipeline.py:874` (`preview_frame`).

### 2. Direction, which is free

**Yaw is just which columns get cropped, with wraparound.** No resampling, no
quality loss, no measurable cost. Worth designing around: once a preview frame
has been rendered, changing direction is a pure re-crop, so the UI can update
instantly without recomputing depth.

Pitch is deliberately not offered. Tilting a VR180 field puts the horizon
off-level in the headset, which is uncomfortable; roll is worse. Yaw-only is
both easier and more correct, and it keeps the field a clean rectangle in
equirect — add pitch and the region becomes a curved lens shape that is much
harder to draw and to drag.

### 3. Metadata

- `stereo_mode="left-right"` at `pipeline.py:773`
- Parameterise the `equi` bounds in `_sv3d()` (`spherical.py:66`), which
  currently hardcodes all-zero, meaning "the whole sphere". For a 180° field the
  horizontal bounds crop a quarter from each side. Verified by hand in the
  spike: the change is a parameter, not a rewrite, and ffprobe reads the result
  back correctly as `tiled equirectangular`.
- **Spherical Video V1** (`spherical.py:34`) cannot express a partial sphere.
  Omit it in 180 mode; check nothing depends on it first.

### 4. Detection, for refusal

Not to handle 180 input — to reject it clearly. ffprobe exposes everything
needed:

```
projection: "tiled equirectangular"
bound_left: 3841   bound_right: 3839   bound_top: 0   bound_bottom: 0
Stereo 3D: side by side
```

Field of view falls straight out of the bounds, which are pixels *outside* the
frame:

```
fov = 360 * width / (width + bound_left + bound_right)
```

Cases worth distinguishing, each with its own message:

| input | response |
|---|---|
| 180 mono | "this looks like a 180° crop — the tool needs the original 360° footage" |
| any stereo input | "this is already 3D" |
| dual fisheye | hard to detect reliably; fails the aspect and metadata checks and gets a generic message |

For untagged files, aspect ratio is a usable hint *because the input is
monoscopic*: 1:1 is a half-equirect, 2:1 is a full one. It would be ambiguous
otherwise, since a side-by-side 180 is also 2:1. An explicit
`--input-projection` override stays available.

### 5. UI

- an output mode selector: **360 VR** (top-bottom, the default) or **VR180**
  (side-by-side)
- when VR180 is selected, a direction control: the equirect thumbnail with a
  draggable band showing the 180° field, wrapping at the edges, and the
  resulting view beside it

Optional nicety: suggest a starting yaw from the frame — the direction with the
most depth variation, say — so the user is nudged toward the interesting half
rather than the sky.

### 6. Audio: rotation stops being optional

The yaw control is exactly the feature that makes ambisonic rotation
**mandatory**. Point the field somewhere other than the source's forward
direction and every sound sits in the wrong place — and in 180 that is worse
than in 360, because a source that should be visible in front can land behind
the viewer, in the hemisphere that no longer exists.

**Built.** See `stereo360/ambisonics.py`. Easier than feared, and the reason is
worth recording: a rotation about the *vertical* axis needs no Wigner-D matrix
at any order. In real spherical harmonics it never mixes one degree with
another and never touches the m = 0 channels — each (+m, −m) pair simply turns
by m times the angle, which is the angle-sum identity and nothing more. Exact,
order-independent, and indifferent to SN3D versus N3D.

It is a linear mix of channels, so ffmpeg's `pan` filter expresses it directly
and nothing has to be decoded into Python.

Three things that had to be measured rather than assumed:

- **`NC`, not `Nc`.** Lowercase asks for the *default* layout of N channels and
  there is none for 9, so second order would not have run at all. Uppercase
  asks for an unknown layout, which is what ambisonics is.
- **AAC will not accept an unknown layout** ("Unsupported channel layout '4
  channels'"), so the chain relabels to 4.0 afterwards. Found by a real render
  failing, after the unit tests passed against raw PCM.
- **A named layout is not harmless.** `pan=quad` loses one channel and
  duplicates another by the time it reaches the file.

The rotation forces a re-encode — there is no remixing channels without
decoding them — so **which** encoder matters, and ffmpeg's native `aac` is not
on the list at any priority. It will encode four channels quite happily and
sounds materially worse than libfdk_aac at the same bitrate; picking it because
it is the one spelled "aac" is a well-worn way to quietly degrade a master.

The order is libfdk_aac → libopus → pcm_s24le, chosen by probing rather than
tabulating, because the answer depends on the build *and* the order:

| | 4 ch | 9 / 16 ch | notes |
|---|---|---|---|
| libfdk_aac | best, if present | untested | not in this build — its licence keeps it out of most Windows ones. FDK is 7.1-limited for AAC-LC, so 9/16 probably fails; the probe settles it per build rather than this table |
| libopus | works | works | Opus-in-MP4 ambisonics unverified on any headset |
| pcm_s24le | works | **no** | lossless; MP4 refuses PCM with an unnamed layout |
| flac / alac | work | no (8 ch max) | ALAC silently mangles 16 ch — avoided |

Channel order survives every combination offered — verified by
cross-correlating each output channel against each input one, after an
FFT-peak method wrongly reported Opus permuting the higher orders and nearly
cost them their support.

### Opus says it is ambisonic, and RFC 8486 does carry into MP4

Opus tracks are written with **channel mapping family 2** — RFC 8486's
ambisonic family: ACN order, SN3D, (n+1)² channels, which is ambiX exactly.

The reasonable doubt is that RFC 8486 signals this in **Ogg**'s `OpusHead` and
this tool writes MP4. It carries anyway, because the family is a property of
the Opus *stream*, not of Ogg: MP4's `dOps` box (OpusSpecificBox) mirrors
OpusHead field for field — version, channel count, pre-skip, sample rate,
gain, **ChannelMappingFamily**, then the mapping table. Read back from a real
render: `family=2, streams=N, coupled=0, mapping=[0..N-1]` at every order.

Family 2 and family 255 encode to identical structure — same stream count, no
coupling, same channel order, same file size to the kilobyte — so this costs
nothing. What it buys is self-description: with 255 ("discrete channels, no
meaning") the only thing in the file calling the track a soundfield is
Google's SA3D box. With 2 the audio stream says so itself, and the two agree.

One caveat to keep in mind for device testing: the Opus-in-ISOBMFF
encapsulation spec predates RFC 8486 and normatively references RFC 7845,
which defines only families 0 and 1. The field is a passthrough byte and
ffmpeg writes it happily, but a player may reject a family it does not know,
where 255 invites it to hand the channels over regardless. If a headset
refuses an Opus file, that is the first thing to try changing.

### There is no "rotate by metadata" field, and it was worth checking

The appealing alternative is to leave the samples alone and write the offset
as a tag. Three places it could plausibly live, all checked:

- **SA3D** — no rotation field. It carries version, type, order, ordering,
  normalisation, channel count, and a channel *map*, and the map is an index
  permutation. That is not enough even for a right angle: a 90° yaw needs
  matrix entries of −1 and a 45° yaw needs ±0.707. Only a yaw of zero is a
  permutation.
- **`sv3d > proj > prhd`** — this *does* carry 16.16 yaw/pitch/roll, and it
  round-trips: write 45 and ffprobe reads back `yaw: 45` in the Spherical
  Mapping side data. But it is in the **video** sample entry and moves the
  picture. Using it would be the opposite manoeuvre — leave the soundfield
  alone and declare the video turned — which puts the content beside the
  viewer instead of in front of them. Left at zero, which is also the truthful
  value once the crop and the rotation have both happened.
- **Opus `dOps`, mapping family 3** — the only real matrix in any of it.
  RFC 8486 family 3 carries a demixing matrix, and a rotation genuinely could
  be folded into it: metadata-only rotation, no samples touched. Two blockers.
  ffmpeg cannot write family 3 ("Failed to create encoder: request not
  implemented"), and it saves nothing unless the source is *already* Opus,
  which ambisonic camera output never is — from AAC you would re-encode to
  Opus to get there.

The concern underneath the question is quality, and that is already solved
from the other end: `--ambisonic-codec pcm_s24le` makes the rotation lossless.
The source is decoded once, which playing it would do anyway, and written back
without compression. No generation is lost, so metadata-only rotation would
buy nothing but file size.

### Why PCM is not the last resort

PCM deserves its place rather than being a fallback: 4 channels of 24-bit
PCM is about 1.2 Mbit/s beside an 8K picture running fifty times that, and it
makes the rotation cost nothing at all. `--ambisonic-codec` forces any of them,
since "will my headset play Opus" is a question only the user can settle.

Plain stereo is left alone: a two-channel bed has no soundfield to turn and is
usually head-locked deliberately. Four channels with no `--spatial-audio` gets
a warning, since that is a forgotten flag rather than a decision.

## Frame size, and why 180 lands well

Both codecs cap the decoded picture at **35,651,584 luma samples** at the
highest level either defines. HEVC states it directly as MaxLumaPs for levels 6
through 6.2; H.264 states it as 139,264 macroblocks at levels 6 through 6.2,
and 139264 × 256 is the same number. **Switching encoder buys nothing.** Width
and height individually are fine to about 16,888 px; the area is what is
capped.

| Output | Frame | Megapixels | Within the cap |
|---|---|---|---|
| 360 top-bottom, 8K source | 7680×7680 | 59.0 | **no — 1.65× over** |
| 360 top-bottom, 5.7K source | 5760×5760 | 33.2 | yes |
| **VR180 side-by-side, 8K source** | 7680×3840 | 29.5 | **yes — confirmed on a Quest 3** |

The current flagship 360 output is out of spec; VR180 from the same source is
not. A real argument for the feature beyond format preference.

**But it is not an argument against 7680×7680**, and the interface must not
read as one. Out of level is exactly what an 8K 3D-360 YouTube master looks
like: YouTube transcodes on ingest, where software decode ignores levels
entirely, and there is no smaller frame that carries 8K per eye in top-bottom.
The cap is a constraint on *direct playback* — a headset decoding the file
itself — and on nothing else. Encoders make no fuss either way: x264 warns and
tags level 6.2 regardless, x265 stays silent and invents "Level-6.3", which
does not exist. Both files decode in software.

## Device targets

### Quest 3

Reads Google Spherical Video V2 — the boxes this project already writes. With
`left-right` stereo mode and correct `equi` bounds, a VR180 file should be
recognised natively. This is the lower-risk target and should be made to work
first.

### Apple Vision Pro

Three tiers, in increasing order of work and decreasing order of certainty:

**Tier 1 — third-party player.** A standard MP4, side-by-side, equirect-with-
bounds. Several 360/180 players on visionOS read this, and most allow the
layout to be set manually if metadata is not picked up. That manual override is
the safety net: even if nothing reads the boxes, the file still plays.
*Should work with exactly the Tier-1 Quest output — one file, both devices.*

**Tier 2 — native Photos playback.** Apple's immersive handling uses its own
signalling rather than Google's. Recent visionOS added native 180°/360°
support through Apple's projected-media metadata. In principle both sets of
boxes can live in one file, since unknown boxes are skipped — which would give
one file that is native on both devices. **Unverified.** I do not know Apple's
current requirements well enough to commit to this, and it needs checking
against the actual specification before any work starts.

**Tier 3 — MV-HEVC. Blocked on Windows. Measured, not assumed.**

Apple's native spatial video packs two views into a single HEVC stream. Three
independent blockers, checked against this machine (ffmpeg 8.1.2 gyan.dev full
build, x265 4.2+37 — about as complete as Windows ffmpeg gets):

*x265 has no multiview compiled in.* Probing the parameter parser:

| `-x265-params` | Response |
|---|---|
| `num-views=2` | Unknown option |
| `multiview-config=...` | Unknown option |
| `bogusoption=1` | Unknown option |
| `alpha=1` | *recognised* — a real error about the alpha plane |

`num-views` draws exactly the response an invented option does, so the
multiview extension is absent. `alpha` being recognised shows the multi-layer
scaffolding from x265's 4.x work is partly present — this is a build flag
(`ENABLE_MULTIVIEW`) being off, not a version problem. Building x265 from
source with it on is feasible but a real undertaking.

*ffmpeg cannot drive it even if x265 could.* The libx265 wrapper exposes zero
multiview options, and structurally feeds a single stream of frames to the
encoder. MV-HEVC needs two synchronised views; no ffmpeg command expresses
that. Note the asymmetry — ffmpeg 8.1.2 **can decode** MV-HEVC (`-view_ids`,
`-view_ids_available`, `-view_pos_available`, exporting `AVStereo3DView`). It
reads Apple spatial video and cannot write it. That gap is the work.

*Packaging is a third problem.* An MV-HEVC bitstream still needs Apple's `vexu`
boxes to be treated as spatial. ffmpeg's muxer does not write them — though
`spherical.py` already hand-writes MP4 boxes, so this part is within reach.

Custom x265 build, plus ffmpeg work that does not exist, plus hand-rolled
packaging, plus no way to verify the result from Windows (see below). Not a
milestone — a research project. Revisit if ffmpeg gains MV-HEVC encoding.

### There is a simulator, but it will not answer the question

The visionOS simulator ships with **Xcode, which is macOS-only**. No Windows
version and no workaround.

More important than the OS: **the simulator renders flat.** It runs in a window
on a Mac's 2D display and cannot present stereo. It would confirm that a file
loads, parses and plays, and that metadata is recognised — real format
validation — but it cannot show whether the 3D looks right, which is the only
question worth asking about output like this.

So a Mac does not substitute for a device here. Options, cheapest first:

- **Someone with a physical Vision Pro.** Beats the simulator outright, because
  they can see the stereo. Also the cheapest.
- **A cloud Mac by the hour** (MacStadium, MacinCloud, AWS EC2 Mac) for Xcode
  and the simulator. Enough to answer "does it parse", nothing more.
- A used Mac mini, if Tier 2 or 3 is ever pursued seriously.

### Recommended target

**Tier 1.** One file, side-by-side VR180, Google Spherical V2 — produced
entirely from Windows with no Apple tooling in the chain, and already confirmed
playing on a Quest 3. Tier 2 is worth revisiting once someone can test on a real
Vision Pro; Tier 3 is out of reach from this platform.

## Spatial audio

Ambisonics carries over unchanged, and structurally rather than by luck. `SA3D`
goes into the *audio* sample entry (`spherical.py:267`) while `st3d` and `sv3d`
go into the *video* one — separate tracks describing different things — and
audio is copied with `-c:a copy` (`ffmpeg_io.py:512`) without passing through
projection logic at all.

More fundamentally, **ambisonics has no field of view.** A first-order ambiX
track encodes a full soundfield; there is no such thing as "180° ambisonics",
and the channel count is projection-independent.

The exception is the yaw control, which needs rotation — see "Audio: rotation
stops being optional" above.

### One coupling to confirm

Section 2.4 proposes dropping the Spherical Video **V1** block in 180 mode,
since V1 cannot express a partial sphere. That must not disturb audio, and it
should not: V1 is video-only RDF, spatial audio was always V2/SA3D, and the two
go to different tracks. Worth an explicit test rather than an assumption — this
is exactly the kind of coupling that stays invisible until a file plays silent.

### The mismatch is a production question, not a code one

Full-sphere audio against a half-sphere picture. A source behind the viewer is
still rendered behind them, correctly, with nothing there to look at.

Usually that is desirable — it is much of why VR180 feels present rather than
like a screen — but it can be odd when a rear source is prominent enough to
make someone turn, only to find the video has ended. Some VR180 productions
attenuate or fold the rear hemisphere in post for that reason.

That is a creative decision and should stay out of the tool by default: it is
destructive, opinionated, and irreversible once applied. If it is ever wanted
it belongs behind an explicit flag, and doing it properly means real ambisonic
rotation and beamforming, not channel arithmetic.

### Device support mirrors the video tiering

| Target | Ambisonic audio |
|---|---|
| Quest 3 | Reads SA3D ambiX. Same path as 360 — expect it to work. |
| Vision Pro, third-party player | Depends on the player. Some handle ambiX, some downmix to stereo. |
| Vision Pro, native | Apple's immersive audio uses its own format rather than SA3D. Unverified — the same uncertainty as the video metadata in section 6. |

Also worth knowing: a lot of VR180 content ships plain stereo or binaural
rather than ambisonics, because the field is fixed forward. The tool already
handles that correctly — `--spatial-audio` is opt-in and refuses any track
whose channel count is not a perfect square (`spherical.py:273`), so a stereo
source cannot be mislabelled as ambiX by accident.

### Do not *replace* ambisonics with binaural

If a target only accepts binaural, the obvious thought is to render the
ambisonics to binaural here. It is technically possible and it is the wrong
move.

Binaural is a *rendering*, not a format. At playback the renderer rotates the
soundfield to the listener's current head orientation and only then decodes it
through HRTFs — and it redoes that on every tracking update. Baking the
rendering offline means choosing one orientation and freezing it: turn your
head afterwards and the whole soundfield turns with you, so a source on your
left stays on your left forever. You would keep spatialisation (elevation,
front/back, externalisation) and lose head tracking, which is the part that
makes it a place rather than headphones.

There is no correct orientation to bake, because the right one changes several
times a second. That is the "the head has to match the video" problem taken to
its conclusion: it is the reason not to bake, not a complication to solve
alongside baking.

None of that is an argument against a binaural *fallback* track — see below.
It is an argument against binaural being the only thing in the file.

**Check the premise first.** "Not supported natively" is not "not possible" — a
player app can decode ambisonics itself and render against the headset's
orientation API, which is how most VR video players work on every platform.
Which visionOS players do this is worth finding out before engineering around
the assumption that none do.

### A fallback should be binaural, not a stereo downmix

MP4 carries multiple audio tracks, so a fallback goes *beside* the ambisonic
one rather than replacing it.

It should be binaural. The objection above — that baking destroys head tracking
— does not apply here, because the fallback is only ever reached by a player
that cannot do ambisonics, and such a player cannot do head-tracked audio at
all. The real comparison is head-locked binaural against head-locked stereo,
and binaural keeps the elevation, front/back disambiguation and externalisation
that a downmix discards for nothing in return. This content is heard through
headphones in a headset; it is essentially never played on speakers.

Cheaper than it sounds, and needs no Python dependency: decode ambiX to a
virtual speaker layout with `pan`, then HRTF-convolve with `sofalizer`. The
local ffmpeg has `sofalizer`, `headphone` and `--enable-libmysofa`. The only
addition is a SOFA HRTF file — freely available under permissive licences
(SADIE II, MIT KEMAR), a few MB, shipped or fetched once.

Trade-offs, none of them decisive:

- Generic HRTFs vary by listener; some get poor externalisation or front/back
  confusion. That argues for picking a well-regarded set, not for avoiding
  binaural.
- Nothing in the container signals "this is binaural". Played on speakers it
  sounds narrow and phasey — odd, not broken.
- Quest 3 uses open-ear speakers, so there is crosstalk. Meta ships head-tracked
  spatial audio to those speakers routinely, so it evidently holds up.

### Track selection is the harder half

A fallback only helps if the right player picks the right track — and a player
that cannot read `SA3D` is by definition not clever about this. It will take
track 0, or whichever is flagged default.

If that is the 4-channel ambiX, it plays W/X/Y/Z as discrete channels. W is
omnidirectional and X/Y/Z are figure-eights, so the result is not
"unspatialised", it is actively wrong. **A badly ordered fallback is worse than
no fallback.**

That points to the binaural track being the default and ambisonics the
alternate — which then relies on ambisonics-capable players actively seeking
the `SA3D` track rather than taking the default. Most presumably do; some may
only inspect track 0. Needs testing on both devices before a layout is fixed.

### Do not build the fallback speculatively

Test ambisonics on Quest 3 and on whichever visionOS player is settled on
first. If both handle it, a fallback is insurance that introduces the selection
problem above and could make things worse. Build it when something is shown to
need it.

Each step leaves 360 working and the tests green.

## Phase 1 results

The throwaway spike, run before any implementation. Padded the 180 source into
a full equirect canvas, ran the unmodified pipeline, cropped back to
side-by-side. Nothing was built on it.

**Depth survives, but the padding fill decides whether it does.** Measured
against depth from the true full 360 of the same scene, over the directions the
180 field covers, affine-fitted first since relative depth has arbitrary scale:

| fill | correlation | residual |
|---|---|---|
| black — what this plan originally proposed | 0.375 | 0.178 |
| grey | **−0.106** | 0.191 |
| **mirror** | **0.905** | **0.082** |

Black gives 37% correlation. Grey is *negative* — actively anti-correlated;
both invent a bright dome where the fill meets real content. Mirror recovers
90%. The original reasoning ("the empty hemisphere will corrupt depth
normalisation") was right about the failure and wrong about the cause: it is
not hemispheres the model objects to, it is **discontinuities**. Plausible
continuation across the boundary removes most of the problem.

That matters for 2.1. If reflecting content across the boundary works this well
in equirect space, padding each face's empty region may be cheaper than
restructuring the face set — worth testing before committing to the larger
design.

**Two costs remained even with the best fill:**

- depth range compressed to **0.59×** the reference, because the mirrored scene
  contains the same content twice and the percentile normalisation narrows.
  Directly weakens the stereo. Fixable by normalising over the real region only.
- the ground was **4.7× worse than the horizon**, rising to 2.4× worse again at
  the field edge — which is what produced the pole-boundary finding in 2.1.

**Confirmed on device.** `spike_vr180_quest.mp4` (7680×3840 side-by-side, 29.5
Mpx, 41 Mbit/s, `st3d` left-right, `equi` bounds 0.25) plays on a Quest 3, and
the reported artefact was the floating ground above — not a format problem.

# Appendix: 180 input, not planned

Kept because the analysis was done, and because the reasoning would need
revisiting if monoscopic VR180 ever became common. It is not expected to.

Everything below describes what supporting **180 input** would take. None of it
is needed for 360 → 180 output.

#### 2.1 Face layout for a hemisphere — the main job

**Why it is not optional.** Feed a 180° source to the current six faces and
four of them come back half black. A relative-depth model normalises against
what it sees, so a half-black face produces a depth map normalised against the
black. That is not wasted compute, it is *wrong output*.

**What is needed.** A face set covering only the front hemisphere. The
machinery is close to hand — `_FACE_BASIS` is a dictionary of basis vectors,
and `_overlap_face_dirs` already builds arbitrary-FOV faces from one — but two
things assume a closed cube:

- `_face_local_coords` resolves a direction to its owning face across all six
- `align_overlapping_faces` finds face pairs by asking which face owns each
  sampled direction

For a hemisphere those need an explicit adjacency set rather than a lookup over
the whole cube.

**Open design question**, worth settling before writing anything: whether a
hemisphere is best covered by a subset of cube faces, or by a purpose-built
layout (for example one centre face plus four surrounding at a shallower
angle). The cube exists because it tiles a *sphere* evenly; it has no special
claim on a hemisphere.

**One constraint on that choice is already settled: do not centre a face on a
pole.** The field boundary passes through the nadir and the zenith (see
[section 4](#the-edge-is-not-the-left-and-right-sides)), so a face centred
there is split through its middle by the edge — the worst possible
arrangement. Faces should be placed so the boundary falls along their *edges*.
That rules out inheriting the cube's ±Y faces, which is the obvious starting
point and the wrong one.

Measured in the phase 1 spike, where padding made four of six faces 50%
fabricated:

| region | error at field centre | at the field edge |
|---|---|---|
| horizon (`+Z` face, 0% fabricated) | 0.020 | 0.023 |
| ground (`-Y` face, 50% fabricated) | **0.095** | **0.224** |

The ±X faces were equally fabricated but fared far better, because the
boundary splits them cleanly left from right. The down face is split through
the nadir, so real and invented content interleave around the pole. That is
what showed up in a headset as a patch of ground floating above the rest of
the scene.

#### 2.2 Longitude wrap must become clamp — seven sites

In 360 the left and right edges of a frame are the same place. In 180 they are
90° apart. Every wrap is wrong in the new mode, and each will show as content
bleeding from one edge of the field to the other — subtle on a monitor, obvious
in a headset.

| File | Line | What |
|---|---|---|
| `projection.py` | 283 | `equirect_to_cubemap` — `BORDER_WRAP` |
| `projection.py` | 882 | `equirect_to_overlapping_faces` — `u % w` |
| `projection.py` | 886 | same — `BORDER_WRAP` |
| `warp.py` | 381 | `_directional_fill` — `np.mod(src, w)` |
| `warp.py` | 664 | pass 1 splat — `np.mod(u0, w)` |
| `warp.py` | 762, 767 | pass 2 — `su % w` and `BORDER_WRAP` |
| `warp.py` | 796 | hole fill — `BORDER_WRAP` |
| `warp_torch.py` | 228 | GPU pass 2 — `su.remainder(w)`, plus the wrapped
  column padding either side of the image |

Note the GPU path pads the image with one wrapped column on each side before
`grid_sample`, because it has no wrap mode. In 180 that padding must replicate
rather than wrap.

**This is the highest-risk item for the 360 path**, because every one of these
lines is on the hot path of working code. See
[Not breaking 360](#not-breaking-360).

## Disocclusion at the field edge

Warping the second eye shifts everything sideways. With 180 input there is
genuinely nothing beyond the edge, so one side of the frame ends up with a strip
the second eye has no source for. Missing information, not a bug — and the
reason 360 input produces a better result.

#### The edge is not the left and right sides

It is easy to picture the field boundary as two vertical lines. It is not.
A 180° field is |longitude| ≤ 90, and lon = ±90 is the great circle through
**both poles** — so the boundary runs down the left side, across the point
directly beneath your feet, up the right side, and back over your head.

**The ground is cut in half by the field edge, through the nadir.** Same for
the sky through the zenith. Anything reasoning about "the edge" — disocclusion
fill, clamping, face coverage — has to account for a boundary that passes
through the floor, not just two side walls.

Found by the phase 1 spike rather than by reading the geometry, which is
the argument for having run it. See 2.1 for what it means for the face
layout.
